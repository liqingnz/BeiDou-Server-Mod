01连接服务器

两个别名指向同一台机器，区别只在要不要开管理后台隧道。配置在本机 C:\Users\liqin\.ssh\config。

普通登录 · 可同时开多个任意目录
$ ssh beidou
带管理后台隧道 · 同时只能开一个任意目录
$ ssh beidou-tunnel
# 保持这个窗口不关，浏览器访问 http://localhost:18686

隧道把本机 18686 转发到服务器上只绑回环的 8686。管理后台没有暴露在公网，这是唯一的访问途径。

为什么本地端口是 18686 而不是 8686

本机开发环境自己占着 8686。用不同端口既避免冲突，也让你一眼分清：localhost:8686 是本地开发，localhost:18686 是生产。

隧道只能开一个

已经开着 beidou-tunnel 时再开第二个会失败（本地端口被占）。日常操作用 ssh beidou，需要看后台时才用带隧道的那个。

02命令与工作目录

这是最容易踩的坑。命令分两类，本手册每个命令板右上角都标了它属于哪一类。

命令工作目录原因
free -h uptime df -h ss -tln任意目录读 /proc 的系统级信息，与路径无关
docker ps docker stats docker logs 容器名任意目录直接与 dockerd 通信，不读配置文件
docker compose 任何子命令/opt/beidou要读当前目录的 docker-compose.yml 和 .env

在错误目录敲 docker compose 会报 no configuration file provided。养成习惯：登录后先切过去。

登录后的第一条命令任意目录
$ cd /opt/beidou

03日常查看

按使用频率排列。看日志是排查一切问题的起点。

容器状态 · 最先看这个/opt/beidou
$ docker compose ps
实时日志 · Ctrl+C 只退出查看，不停服/opt/beidou
$ docker compose logs -f beidou-server
只看最近 100 行/opt/beidou
$ docker compose logs --tail 100 beidou-server
内存 · 重点看 Swap 那一行任意目录
$ free -h
各容器内存与 CPU任意目录
$ docker stats --no-stream
重启服务端 · 数据库不动/opt/beidou
$ docker compose restart beidou-server
断开 SSH 不影响服务

容器是 dockerd 的子孙进程，不属于你的登录会话。关终端、关电脑、断网都不影响服务器上的运行。restart: unless-stopped 还保证了崩溃后自动重启、服务器重启后自动拉起。

04发布更新

改完代码到上线，本机只需要 push，编译由 GitHub Actions 完成。服务器永远不参与构建。

步骤在哪做什么
1本机 IDEA改代码，提交到 master 并 push
2GitHubActions 自动构建并推送镜像到 ghcr.io（约 10–20 分钟，等绿灯）
3服务器docker compose pull 再 up -d
拉取新镜像并替换容器/opt/beidou
$ docker compose pull
$ docker compose up -d

没有第三步。代码、wz、脚本全部烤在镜像里，不使用「首次拷贝到卷」那套机制，所以不存在「换了新镜像但跑的还是旧 jar」的陷阱。

镜像分层的好处

Dockerfile 里 wz（561 MB，几乎不变）在前、jar（113 MB，每次都变）在最后。日常改 Java 代码只有最后那一层需要重新传输，wz 层直接复用缓存。改 Dockerfile 时不要打乱这个顺序。

清理旧镜像 · 磁盘紧张时执行任意目录
$ docker image prune -a -f

05监控与预警

这台机器内存很紧，2 GiB 标称、系统可见 1.6 GiB。只需要盯一个指标。

2026-08-15 事故 · 待修复项未执行

部署当天打开管理后台后整机失去响应，SSH 无法进入，需要从控制台重启。下方的 swappiness 与 -Xmx 修复尚未执行——重新拿到服务器后先做第 05 节末尾的《恢复后必做》。

核心指标：load average（不是 Swap）

直觉上该看内存，但这台机器上 Swap 会给出虚假的安全感：系统设了 vm.swappiness=0，濒死时 Swap used 依然是 0。事故当时的实测就是 Swap used = 0B 而 load 已经 18.5。

最该常看的一条任意目录
$ uptime
load average（2 核机器）状态处理
低于 1.0正常不用管。实测 1 玩家在线时为 0.50
2.0 上下满载两个核都跑满了。看看是不是玩家变多，或后台开着
两位数雪崩进程堆积在等 I/O，很快会连不上 SSH。立刻 docker stop beidou-server

辅助指标：Swap

把 swappiness 调到 30 之后，Swap used 才重新具有预警价值——那时它不为 0 表示内核开始换出冷的 JVM 堆页，是正常的减压行为；持续增长到数百 MB 才需要处理。

基线数据（2026-08-15 首次部署实测）

项目零玩家1 玩家在线
beidou-server732.2 MiB752.5 MiB
beidou-db270.5 MiB293.0 MiB
系统可用内存145 MiB100 MiB
Swap 已用0 B0 B
负载均值（2 核）—0.50 / 0.64 / 0.45

CPU 完全不是瓶颈。内存是唯一约束。已知有人在同样 2 GiB 的机器上跑到 20 人同时在线正常。

一次看全：负载 + 内存 + 容器/opt/beidou
$ uptime && free -h && docker compose ps

恢复后必做

这三步针对 08-15 事故的根因，重新拿到服务器后按序执行。

先抢在 JVM 之前

restart: unless-stopped 意味着开机后容器会自动拉起，用的仍是旧参数。SSH 一通就先停掉它，否则内存又会被吃满、重新失去控制权。

1 · 抢回控制权任意目录
$ docker stop beidou-server
2 · 让内核肯用 swap（根因修复）任意目录
$ sysctl -w vm.swappiness=30
$ echo 'vm.swappiness=30' > /etc/sysctl.d/99-beidou.conf
3 · 降低 JVM 堆上限后重启/opt/beidou
# 把 .env 里的 JAVA_OPTS 改成：
# JAVA_OPTS=-Xms384m -Xmx768m -XX:MaxMetaspaceSize=160m
$ docker compose up -d
为什么 swappiness 是根因

swappiness=0 让内核拒绝换出匿名内存（JVM 堆），可用内存只剩 90 MiB 时它只能反复回收页缓存，于是 JVM 和 MySQL 需要的可执行页被不断驱逐又从磁盘读回——这叫页缓存抖动。经济型实例的云盘 IOPS 基线低，进一步放大成雪崩。

换出冷页只损失一点性能，反复重读可执行页是灾难性的。配了 2 GB swap 却设 swappiness=0，等于白配。

不要盲目下调 -Xmx

上面第 3 步是针对已发生事故的定向修复。除此之外，没有明确信号时不要动 JVM 参数——-Xmx 调太小会触发 JVM 内部 OOM，那比换页严重得多：换页只是卡，OOM 是直接崩。

06备份与恢复

只有一个目录装着不可重建的东西：玩家数据。镜像和配置随时能从 git 与 ghcr.io 重建。

路径内容要不要备份
/opt/beidou/docker-db-dataMySQL 全部数据：账号、角色、装备、仓库必须
/opt/beidou/.env数据库密码、JWT 密钥建议
/opt/beidou/logs运行日志不需要
镜像代码、wz、脚本不需要

热备份（不停服，推荐）

导出 SQL 到 /root，带日期戳/opt/beidou
$ docker compose exec -T beidou-db \
    sh -c 'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction \
    --routines --events --databases beidou' \
    | gzip > /root/beidou-$(date +%Y%m%d-%H%M).sql.gz

--single-transaction 是 InnoDB 一致性快照，导出期间玩家可以照常在线。

下载到本机

在本机 PowerShell 执行任意目录
> scp beidou:/root/beidou-*.sql.gz E:\备份\

恢复

先停服务端，只留数据库/opt/beidou
$ docker compose stop beidou-server
$ gunzip < /root/备份文件.sql.gz | docker compose exec -T beidou-db \
    sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD"'
$ docker compose start beidou-server
备份要放到别的地方

和数据库在同一块云盘上的备份，盘挂了就一起没了。定期 scp 下载到本机或对象存储。

07故障排查

按症状查。绝大多数问题第一步都是看日志。

症状最可能的原因怎么办
玩家连不上登录服 阿里云安全组没放行，或容器没跑 先 docker compose ps；容器正常就去控制台查安全组 8484 / 7575-7577
能登录，卡在选频道 WAN_HOST 填错 它是发给客户端去连频道服的地址，必须是公网 IP。改 .env 后 up -d
管理后台打不开 没开隧道，或访问了 8686 要 ssh beidou-tunnel 且窗口保持打开，浏览器访问 18686
服务端反复重启 数据库连不上，或内存 OOM docker compose logs --tail 200 beidou-server 找 Caused by
游戏卡顿、延迟高 内存压力 uptime 看 load average，见第 05 节
能 ping 通、端口能连，但 SSH 卡在握手 用户态被内存压力饿死（不是网络问题） ICMP 和 TCP 握手都在内核里完成，所以网络看着正常。走阿里云控制台 Workbench 执行 docker stop beidou-server；进不去就重启实例，然后立刻做第 05 节《恢复后必做》
磁盘告警 旧镜像堆积 docker image prune -a -f；日志已配轮转（10 MB × 3），不会无限涨
no configuration file provided 不在 /opt/beidou cd /opt/beidou，见第 02 节
拉镜像超时 Docker Hub 在国内不通 已配 daocloud 加速器。自己的镜像走 ghcr.io，直连正常
排查起手式：只看错误行/opt/beidou
$ docker compose logs --tail 300 beidou-server | grep -E 'ERROR|Caused by|OutOfMemory'
日志里的 Exception 不一定是错误

Spring Security 的过滤器链里有个类叫 ExceptionTranslationFilter，正常启动日志里就会出现。搜错误要认准日志级别 [ERROR] 或 Caused by:。

09不要做的事

这些约束都有具体理由，不是洁癖。

  • 不要在安全组放行 8686。Docker 的端口发布直接写 iptables 的 DOCKER 链，优先级高于 ufw——服务器内部的防火墙拦不住它。放行等于管理后台裸奔。
  • 不要在服务器上 docker compose build。前端构建光 Node 就要 1.5–2 GB 堆，2 GiB 的机器必然 OOM。构建交给 GitHub Actions。
  • 不要用不带 -d 的 docker compose up。那是前台附着模式，SSH 断开会把容器一起停掉。
  • 不要把密码写进 docker-compose.yml。那个文件在 git 里。密钥只放 .env，它已被 gitignore。
  • 不要手动改容器里的文件。容器重建就没了。改动要走「改代码 → push → 重新构建」。
  • 不要长时间挂着管理后台。它不是静态页面，前端一加载就并发打一批 API。在只剩百 MiB 余量的机器上这就是尖峰——08-15 的卡死就是这么触发的。看完就 exit 掉隧道。
  • 不要把 Swap used = 0 当成健康。在 swappiness=0 下它濒死时也是 0。看 load average。
